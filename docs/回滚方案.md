## L1 部署回滚 —— 线上出现严重问题

**触发**：线上站点出现功能性故障，需要立即恢复上一个可用版本。

**操作**：
1. 在发布平台的应用管理页（**设置—数据管理—发布的应用**）找到该应用，回滚到上一个版本；或
2. 用基线产物重新发布：
   ```bash
   git worktree add ../logicsim-base baseline-v0
   # 用 ../logicsim-base/public 作为目录重新发布
   ```

**恢复时间**：分钟级

## L2 代码回滚 —— 问题定位到某次提交

**触发**：确认问题由某次提交引入，但不需要放弃整体改造。

**操作**：
```bash
git revert <commit>      # 生成反向提交，保留历史
git push                 # 触发重新部署
```

**⚠️ 实测注意**：`git revert` 对**栈顶提交**干净通过；对**中间提交**可能冲突 —— 因为其后的提交又改动了同一批文件。

- 回滚最新改动（`c1fb9dc`）→ 无冲突
- 回滚中间的改造提交（`53449ca`，其后的 `c1fb9dc` 又改了 `index.html` / `style.css` / `tests/e2e-cdp.js`）→ **报冲突**，需手工解决后再 `git revert --continue`

需要整体回到改造前状态时，**优先用 L3**（独立工作树），比解决冲突更快更可靠。

**恢复时间**：分钟级（栈顶）/ 十分钟级（中间提交 + 解冲突）

## L3 分支回滚 —— 改造整体不可用

**触发**：改造后的代码整体不可用，需要回到改造前状态。

**操作**：
```bash
git worktree add ../logicsim-base baseline-v0
# 用 ../logicsim-base/public 作为目录重新发布
```

**注意**：不要用 `git reset --hard` 抹掉改造提交 —— 那会丢掉 `53449ca` / `c1fb9dc`，需要时只能靠 reflog 找回。用 `git revert` 或独立工作树。

**恢复时间**：十分钟级

**演练结果**：✅ **已验证**。`baseline-v0` 工作树可独立起服务并正常访问（详见下方演练记录）。

## L4 站点回滚 —— 全部失败

**触发**：以上全部失败，或线上环境不可用。

**操作**：直接把用户指引回原站 **https://kuangdash.gitlab.io/logicsim**

该站保持在线且**未被本次改造触碰**，功能与改造前完全一致，是最终兜底。

**恢复时间**：即时（切换链接）

| 操作 | 结果 |
|---|---|
| `git revert --no-commit c1fb9dc`（栈顶提交） | ✅ 干净通过，还原后与 `53449ca` 无差异 |

## 不建议的回滚方式

| 方式 | 为什么不建议 |
|---|---|
| `rm -rf` 删除改造文件 | 不可逆，且无法作为后续重试的基础 |
| `git reset --hard baseline-v0` | 抹掉改造提交，只能靠 reflog 找回 |
| `git push --force` 覆盖远端历史 | 若他人已拉取会造成混乱；本次改造未推送到原仓库，无此需要 |
| 直接删除线上应用 | 会丢失分享链接（重新发布时链接可能变化），应优先用 L1 回滚 |
